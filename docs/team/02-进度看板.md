## 1. 状态与完成度口径

### 1.1 图例

| 图标 | 含义 |
|---|---|
| ✅ | 已通过 / 已完成 |
| ◐ | 进行中 / 已提交待评审 |
| ⬜ | 未开始 |
| ⛔ | 阻塞 |
| — | 不适用 |

### 1.2 Gate 与权重

| Gate | 权重 | 完成标准 |
|---|---:|---|
| G1 设计提交 | 10% | 需求 / 设计 / 接口 / 表 / 测试用例已写入文档 |
| G2 设计冻结 | 10% | 设计评审通过；跨模块契约冻结 |
| G3 编码完成 | 30% | P0 代码可运行；本模块自测通过 |
| G4 单元测试 | 15% | 核心领域 UT 通过；行覆盖 ≥70% |
| G5 集成测试 | 15% | API / DB / Redis / MinIO / WS 集成用例通过 |
| G6 契约测试 | 5% | DTO / 错误码 / WS / 事件 / 回调 fixture 双方一致 |
| G7 E2E | 10% | 对应 P0 E2E 场景通过 |
| G8 验收 / NFR | 5% | 安全 / 性能 / 迁移 / 清理 / 文档 / 进度通过 |

- 完成度 = 已通过 gate 权重之和。
- 当前所有模块仅 G1 提交，G2 待复审，因此完成度统一为 **10%**；这不是编码进度。
- 没有 E2E 不能标 G7；没有安全 / 迁移用例不能标 G8；没有证据不能改百分比。

## 6. 更新规则

1. 模块 owner 在以下时点更新自己行：设计冻结、编码完成、UT 通过、IT / 契约通过、E2E 通过。
2. Score/QA Owner 在 E2E / 性能 / 安全 / 验收后更新对应行与里程碑。
3. 每次更新必须同时写“证据”（PR / CI / 报告）和“日期”；只改百分比不写证据的更新无效。
4. 不允许修改他人模块的进度行；跨模块变更获批后，由目标 owner 更新。
5. 每周至少一次同步；设计复审、发布前必须全量核对。
6. 进度与 `10` 测试文档、`implementation/README` 的模块表保持一致；不一致时以本看板 + 证据为准。
