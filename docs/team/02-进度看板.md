### 1.2 Gate 与权重

| Gate | 权重 | 完成标准 |
|---|---:|---|
| G1 设计提交 | 10% | 需求 / 设计 / 接口 / 表 / 测试用例已写入文档 |
| G2 设计冻结 | 10% | 设计评审通过；跨模块契约冻结 |
| G3 编码完成 | 30% | P0 代码可运行；本模块自测通过 |
| G4 单元测试 | 15% | 核心领域 UT 通过；行覆盖 ≥70% |
| G5 集成测试 | 15% | API / DB / Redis / MinIO / WS 集成用例通过 |
| G6 契约测试 | 5% | DTO / 错误码 / WS / 事件 / 回调 fixture 双方一致 |
| G7 E2E | 10% | 对应 P0 E2E 场景通过 |
| G8 验收 / NFR | 5% | 安全 / 性能 / 迁移 / 清理 / 文档 / 进度通过 |

- 完成度 = 已通过 gate 权重之和。
- 当前所有模块仅 G1 提交，G2 待复审，因此完成度统一为 **10%**；这不是编码进度。
- 没有 E2E 不能标 G7；没有安全 / 迁移用例不能标 G8；没有证据不能改百分比。

### 2.1 关键依赖

```text
M1 → M2 → M3A → M3B → M4 → M7
              └→ M3C → M4
M1 → M5 → M3A
M3B + M3C + M4 → M6
```

- 上游未冻结时，下游只能用 stub；不得把 stub 假设写进正式实现。
- M3A 的 `TaskSnapshot`、M3B 的 `SessionSnapshot`、M3C 的 `RecordingStream`、M4 的 `EvaluationInputManifest` / `EvaluationTerminalEvent` 是关键契约。
- M7 的计算器、排行榜、CSV 可以先用种子数据开发；M6 的模板可以先用 M3A 的只读快照开发。

## 6. 更新规则

1. 模块 owner 在以下时点更新自己行：设计冻结、编码完成、UT 通过、IT / 契约通过、E2E 通过。
2. Score/QA Owner 在 E2E / 性能 / 安全 / 验收后更新对应行与里程碑。
3. 每次更新必须同时写“证据”（PR / CI / 报告）和“日期”；只改百分比不写证据的更新无效。
4. 不允许修改他人模块的进度行；跨模块变更获批后，由目标 owner 更新。
5. 每周至少一次同步；设计复审、发布前必须全量核对。
6. 进度与 `10` 测试文档、`implementation/README` 的模块表保持一致；不一致时以本看板 + 证据为准。

### 8.4 建议顺序

```text
TD-B-01 导出弱标注
  → TD-B-02 人工 golden
  → TD-B-03 真实数据训练 / 评估
  → TD-B-04 shadow 实跑
  → TD-B-05 active 低风险
  → TD-B-06 高风险（条件满足后）

TD-F-01 / F-03 / F-05 / F-07 可与数据线并行
  → TD-F-02 / F-08
  → TD-B-15 + TD-F-09 E2E
  → TD-B-16 NFR
```

- 数据线不阻塞前端轮次 UI；前端轮次 UI 不阻塞 shadow。
- `active` 必须等真实数据评估；不要用合成模型直接放开高风险动作。
- 每次改契约先改 `05A` / `02` / `04` / `09` / `10`，再改实现。

### 8.5 本轮不做

- M3C 录制 / 上传 / 回放（Media/Training Owner）。
- M4 评测、M7 统计、M6 训练（各自 Owner）。
- 自动评价 / 自动标记 / 学生自主举手 / 自动超时（P2，需需求与契约更新）。
- 本地 LLM 实时推理；只保留离线弱标注 / 极端兜底。
