> 上位文档：[需求规格说明书](../requirements/需求规格说明书.md)、[13 代码设计](../design/13-代码设计.md)、[15 代码规范与骨架](../design/15-代码规范与骨架.md)

> 适用范围：M1—M7、M3A/B/C 子工作流、Python AI、前端、数据库迁移、测试与文档

## 1. 原则

1. **一个路径只有一个 owner**：代码、文档、迁移、测试、前端页面都按本文件的归属表划分；不按“谁先看到”或“谁顺手”决定。
2. **Owner 对本模块端到端负责**：设计、实现、迁移、单元 / 集成 / 契约测试、文档和进度；不是只写代码。
3. **跨模块只通过契约协作**：API、DTO、错误码、WebSocket 事件、数据库表 / 外键、集成事件、时间单位、权限码都是契约；先改契约，再改实现。
4. **禁止静默跨模块修改**：包括“只改一行”“只改注释”“只改测试”“只补文档”；必须按第 4 节确认。
5. **完成度以证据为准**：没有测试报告、评审记录或可运行演示，不填“完成”。
6. **先冻结、再并行**：上游接口 / 事件 / 快照未冻结，下游只能用 stub；不得把临时假设写进正式实现。
7. **模块 owner 不互相重构**：发现他人模块问题，提交问题 / 变更请求，由 owner 修改；不直接改。

## 4. 修改规则

### 4.1 本模块修改

Owner 可以在本模块范围内修改：

- 设计文档、实现设计、代码、迁移、测试、前端页面、模块内配置。
- 前提：不改变跨模块契约；不修改共享路径；不删除他人测试。
- 必须：跑本模块 UT / IT；契约变更跑相关契约测试；更新 `docs/team/02-进度看板.md` 自己模块的行。

### 4.2 跨模块修改

默认禁止。确需修改时，按以下流程：

1. **提出变更请求**：在 issue / PR 评论 / 团队频道写清模块、文件、原因、影响、最小方案、测试与回滚；模板见第 9 节。
2. **取得 owner 确认**：目标模块 owner 明确回复“同意 / 执行 / 确认”；口头同意需在 24 小时内补记录。
3. **先改契约**：如果涉及 API / DTO / 错误码 / WS / 表 / 外键 / 事件 / 时间单位 / 权限码，先更新 `02` / `12` / `14` 或模块设计，再改代码。
4. **只改获批文件**：不做顺带重构、不格式化整文件、不改无关行。
5. **验证**：跑目标模块测试 + 受影响契约测试 + 至少一个相关 E2E / 手工用例。
6. **同步**：更新进度看板；通知下游 owner；在 PR 描述中列出所有受影响模块。

**紧急修复**：可先口头确认后动手，但必须在 24 小时内补变更记录；不得以紧急为由跳过测试或文档。

### 4.3 契约清单

以下内容变更视为跨模块变更，必须双方 owner + 架构 owner 确认：

| 契约 | 主要文档 | 发布方 → 消费方 |
|---|---|---|
| `CurrentUser` / JWT claims / 权限码 | `02` / `03` | M1 → 全部 |
| `SchoolCreatedEvent` | `03` / `04` | M1 → M5 |
| `CourseQueryService` / 课程状态 | `03` | M2 → M3 / M6 / M7 |
| `CourseArchivedEvent` / `CourseTeacherRemovedEvent` | `03` / `08` | M2 → M3 / M4 / M6 / M7 |
| `QuestionBankQueryService` / 题目快照 | `04` / `05C` | M5 → M3 |
| `TaskSnapshot` / `TaskPublishedEvent` | `05C` | M3A → M3B / M4 / M7 |
| `SessionSnapshot` / WS 信封 / 事件 / `required_streams` | `02` / `05A` | M3B → M3C / M4 / M6 / 前端 |
| `RecordingStream` / `recording.ready` / 对象键 | `05B` | M3C → M4 / M6 |
| `SubmissionCreatedEvent` | `05A` / `06` | M3B → M4 / M7 |
| `EvaluationInputManifest` / 回调 `(evaluation_id, attempt)` | `06` / `14` | M4 → Python |
| `EvaluationTerminalEvent` | `06` / `07` | M4 → M7 |
| `TrainingRecordSelectedEvent` | `08` | M6 → M4 |
| REST DTO / 错误码 / 分页 / 幂等键 | `02` | 全部 |

| 时间语义（`duration_ms`、t0） | `02` / `05A` / `05B` | M3 / M4 / M7 |

- 契约变更顺序：需求 → `02` / `12` / `14` → 代码 → 测试 → 进度。
- 契约冻结后，下游只能用 stub 或兼容层；不得直接改上游实现“适配自己”。

### 4.4 分支、提交与 PR

- 分支：`feat/<module>-<short>`，例如 `feat/m3a-task-publish`、`fix/m4-callback-idempotency`。
- 提交：`[M3A] 发布任务快照`；一个提交只做一个模块的一件事。
- PR：标题 `[M3] ...`；标签 `module:M3`；跨模块加 `cross-module`；描述列出受影响模块、契约变更、测试命令与结果。
- 一个 PR 默认只改一个模块；跨模块 PR 必须列出所有 owner 的确认。
- 评审：本模块 owner 至少 1 人；跨模块需所有受影响 owner + 架构 owner；跨模块 PR 不得由作者自行合并。
- 不提交他人模块的“顺手修复”；不提交生成物、密钥、预签名 URL、测试录像大文件。

## 5. Agent 跨模块确认规则（强制）

Agent 在编辑任何文件前，必须先判断路径属于哪个模块；**不能只看当前打开的文件，也不能凭文件名猜**。

### 5.1 判断顺序

1. 查 `docs/team/01` 第 3 节的路径表。
2. 如果是 `server/**` 下未列出的新目录、`ai/**` 新 capability、`frontend/src/**` 新页面，先按命名判断模块；无法判断时问用户。
3. 如果是共享路径（第 3.3 节），按共享 owner 判断；涉及多个模块时，视为跨模块。
4. 如果是 `docs/team/01` / `02` 的 owner 表或规则本身，视为全体 owner 契约，必须用户明确指示。

### 5.2 必须询问的情况

目标文件属于以下任一情况时，Agent **停止编辑**，先询问：

- 不属于当前使用者负责的模块（默认 M3A / M3B）。
- 属于共享路径，且当前使用者不是该路径 owner。
- 属于他人模块的测试、迁移、文档章节、前端页面。
- 无法确定归属，或路径表没有覆盖。
- 需要修改 `docs/team/01` 的 owner 表 / 规则。

### 5.3 询问格式

Agent 必须一次说清：

```text
检测到跨模块修改：
- 文件 / 目录：
- 所属模块 / 工作流：
- Owner：
- 修改原因：
- 影响范围（API / 表 / 事件 / 测试 / 前端）：
- 最小修改方案：
- 需要确认的人：

该修改跨出你负责的模块，是否执行？
```

- 只有用户明确回答“是 / 执行 / 确认 / 可以”才继续；回答“先不改”“只改本模块”“问 owner”时停止。
- 一次确认只对一个 PR / 一组列出的文件有效；不得推广到其他文件或其他模块。
- 用户说“你直接改”但未明确模块范围时，仍要先列出文件与 owner，再执行。
- 跨模块修改获批后，Agent 必须：只改获批文件、跑受影响测试、更新进度看板、在最终回复中列出“文件 / owner / 确认人 / 测试结果”。

### 5.4 禁止行为

- 不得以“只是改一行”“只是改文档”“测试失败需要”“顺手重构”为由跳过确认。
- 不得通过修改他人模块来绕过失败测试、接口不匹配或权限问题。
- 不得自行修改 owner 表、模块边界、共享路径归属。
- 不得在跨模块 PR 中夹带无关重构或格式化。

| Gate | 权重 | 完成标准 |
|---|---:|---|
| G1 设计提交 | 10% | 需求 / 设计 / 接口 / 表 / 测试用例已写入文档 |
| G2 设计冻结 | 10% | 设计评审通过；跨模块契约冻结 |
| G3 编码完成 | 30% | P0 代码可运行；本模块自测通过 |
| G4 单元测试 | 15% | 核心领域 UT 通过；行覆盖 ≥70% |
| G5 集成测试 | 15% | API / DB / Redis / MinIO / WS 集成用例通过 |
| G6 契约测试 | 5% | DTO / 错误码 / WS / 事件 / 回调 fixture 双方一致 |
| G7 E2E | 10% | 对应 P0 E2E 场景通过 |
| G8 验收 / NFR | 5% | 安全 / 性能 / 迁移 / 清理 / 文档 / 进度通过 |

- 当前阶段（2026-11-03）：G1 已提交，G2 待设计复审；所有模块完成度按 **10%** 起算。
- 没有 E2E 的模块不能标 DONE；测试未执行的模块不能标 G4—G7。
- 完成度必须附证据：PR、测试报告、评审记录、E2E 报告、演示脚本。

### 6.3 更新责任

| 更新内容 | 责任人 | 频率 |
|---|---|---|
| 本模块 G1—G6 | 模块 owner | 每次设计冻结 / 编码完成 / 测试通过后 |
| E2E / NFR G7—G8 | Score/QA Owner | 每次 E2E / 性能 / 安全运行后 |
| 设计冻结 G2 | Foundation Owner | 评审通过后 |
| 进度看板汇总 | 模块 owner 更新自己行；Score/QA 汇总 | 每周至少一次 |

- 进度看板：[02-进度看板](02-进度看板.md)。
- 不允许把“文档写了”填成“编码完成”；不允许把“mock 通过”填成“集成通过”。

## 7. 测试要求

- 每个模块必须完成 **单元 → 集成 → 契约 → E2E → NFR** 五层；测试层级、准入 / 准出和模块最低组合见 [10 测试与验收](../design/10-测试与验收.md) 第 2 节。
- 模块 owner 编写本模块 UT / IT / CT；Score/QA Owner 编写 `e2e/**` 与跨模块契约；模块 owner 修复本模块缺陷。
- 测试文件也是模块边界：修改他人模块的测试，按第 4.2 节跨模块流程。
- 没有 E2E 的模块不能标 G7；没有安全 / 迁移用例的模块不能标 G8。
- 测试数据、mock、fixture 不得写入真实密钥；外部 AI 只在 staging 手工抽检。

## 8. 冲突与升级

| 冲突 | 处理 |
|---|---|
| 两个 owner 对接口 / 字段有分歧 | 先冻结契约，交 Foundation Owner 主持；必要时回到需求文档 |
| 跨模块修改被拒绝 | 提变更请求或适配层方案；不得直接改对方代码 |
| 设计评审阻断未关闭 | 模块不能进入 G2；下游只能用 stub |
| Owner 请假 / 不可用 | 在 PR 中指定代理 owner，代理只处理已列出的文件；不得长期接管 |
| 安全 / 隐私问题 | 立即通知 Foundation Owner 与 Score/QA Owner；按 Blocker 处理 |
| 进度虚报 | 由 Score/QA Owner 核对证据并回退；重复虚报升级到团队负责人 |
