## 4. M1 板块「日志 + 定时器」结合功能分析

**结论：有。** M1 现有数据基础（`auth_login_events` 登录审计日志、`email_login_codes` 验证码记录、`account_roles` 角色授权）与仓库既有定时器模式（M3 `RecordingRetentionScheduler`、M4 `EvaluationJobScheduler`、`V8 ops.cleanup_jobs`）足以支撑 4 项有实际价值的功能。按价值排序：

### 方案 A：认证数据保留策略定时清理（P1，最推荐）

- **现状**：`auth_login_events`（每次登录/绑定/解绑都写，独立事务，审计失败不影响主流程）与 `email_login_codes`（每封邮件一行，含过期/已消费行）均无清理机制，生产环境下单调增长；`V8__ops_cleanup_jobs.sql` 的清理基础设施类型枚举 `('submission','training_record','temp_attempt','material')` 未覆盖 M1 表。
- **做法**：新增迁移扩展 `ops.cleanup_jobs.root_type` 约束（`login_event`、`email_code`），仿照 M3 `RecordingRetentionScheduler` 实现 `M1RetentionScheduler`：每日凌晨分批删除 N 天前已消费验证码（建议 30 天）与过期未消费验证码（过期即清），登录审计按合规要求保留（建议 180 天，分批删除避免长事务锁表）。
- **实际价值**：控制表膨胀与索引退化（`auth_login_events` 高频写入直接拖慢登录路径）；满足安全审计"日志有保留期限"的通用合规要求。实现成本低、复用既有模式、零业务风险。

### 方案 B：异常登录检测 + 安全提醒（P1，价值高）

- **现状**：`LoginAuditWriter` 已记录 method/provider/success/ip/UA，但只写不复用——失败登录（暴力破解特征）没有任何检测与通知。
- **做法**：定时器（每 5—10 分钟）扫描窗口内聚合 `auth_login_events`：① 同一用户名/IP 连续失败 ≥N 次（如 10 次/10 分钟）；② 同一账号多 IP/多地区成功登录。命中后：写入告警事件表（或复用审计表 `event_type=alert`），通过 `MailSender` 端口（SMTP/Mock 已就绪）向账号绑定邮箱发送安全提醒。
- **实际价值**：把审计日志从"事后取证"升级为"事中发现"；复用 M1 全部既有组件（日志、邮件端口、Redis 限流思想），不需要外部依赖；邮箱未绑定的账号跳过通知只记告警，无侵入。

### 方案 C：账号安全概况页（P2，体验价值）

- **做法（已于 2026-11-25 落地）**：基于 `auth_login_events` 提供只读接口 `GET /api/v1/auth/security/events`（`auth:self`，最近 20 条、上限 50：时间/事件/方式/结果/IP），前端 `/settings/security` 增加「登录记录」卡片。
- **实际价值**：用户可自查异常登录；同时为方案 B 的提醒提供落地页面。数据已存在，只需只读查询 + 一个 Vue 卡片，改动面小。

### 方案 D：验证码限流窗口的自愈清理（P2，低优先）

- **做法**：现有邮箱/IP 小时限流依赖 `countCodesByEmailSince/ByIpSince` 实时查询；定时器每小时把窗口外计数归档，避免限流查询随表增长变慢。
- **说明**：方案 A 落地后此项基本被覆盖，仅当验证码量极大时才独立做。

**不建议做的方向**（经评估无实际价值或超出 M1 边界）：定时轮换 JWT 密钥（无 refresh/吊销机制，轮换会导致全量用户掉线，收益低）；定时清理 Redis OAuth state（Redis TTL 已覆盖，内存实现的清理归入 P1-2 而非新功能）；定时统计角色授权报表（M1 规模下无消费方）。
