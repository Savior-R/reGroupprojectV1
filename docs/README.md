## 阅读顺序

0. 开工前读 [team/01](team/01-模块归属与修改规则.md) 确认模块 owner 与文件边界；每次提交后更新 [team/02](team/02-进度看板.md)。
1. 先读需求规格说明书的第 1—5 章，理解产品边界、角色和模块划分。
2. 开发某个模块前，读第 6 章对应模块的 FR、第 7 章相关用例、第 8—9 章的数据与接口。
3. 再读 `docs/design/` 下对应模块的设计文档。
4. 验收时使用需求规格说明书第 15 章与各模块设计文档的验收章节。

## 文档约定

- **需求基线**：需求规格说明书是当前唯一需求基线，不继承仓库历史文档。历史文档仅作参考，不作为实现依据。
- **编号规则**：
  - 功能需求：`FR-M<模块号>-<序号>`，例如 `FR-M2-05`。
  - 非功能需求：`NFR-<类别>-<序号>`。
  - 接口：`API-<模块>-<序号>`；WebSocket 事件使用小写点号命名，例如 `student.hand_raised`。
- **优先级**：
  - `P0`：MVP 必须完成，缺失则无法形成端到端闭环。
  - `P1`：首个完整版本应完成，可在 MVP 后 6—8 周内交付。
  - `P2`：增强能力，允许延期或按资源裁剪。
- **可追踪**：设计文档中的每个接口、表、页面和测试用例都应引用对应的 FR 编号；无法追踪的内容不进入开发。
- **变更**：需求变更先改需求规格说明书并记录版本，再改设计文档，最后改代码。禁止只改代码不回写文档。
- **模块归属**：每人只修改自己负责的模块；跨模块修改先按 [team/01](team/01-模块归属与修改规则.md) 第 4.2 / 5 节确认。Agent 修改非当前使用者模块前，必须提醒并询问是否执行。
- **进度与测试**：模块完成度、测试执行状态以 [team/02](team/02-进度看板.md) 为准；测试从单元到 E2E 的分层与最低组合以 [design/10](design/10-测试与验收.md) 为准。
