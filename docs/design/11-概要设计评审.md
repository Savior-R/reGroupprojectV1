## 2. 阻断项

### B1 网关认证链路不可实现

**现象**

- `02:30-53` 对全部 `/api/` 启用 `auth_request`，但 `/internal/auth/verify` 只验证 JWT；登录、注册、公开注册选项会被 Nginx 拦截。
- `/_auth` 子请求未带 `X-Internal-Token`，而 `03:127-131` 要求 `/internal/**` 必须带内部 token。
- `02:647-662` 对 `/ws/` 启用 `auth_request`，但 WS 使用 30 秒一次性 ticket，浏览器无法在握手时设置 `Authorization`；`/internal/auth/verify` 也不验证 ticket。
- `00:31` / `02:667` / `10:344` 要求 Nginx 限流，但 `03:112`、`03:469` 明确本轮不做登录 / 注册限流。

**影响**

登录、注册、公开选项不可达；所有课堂 / 面试 WS 握手被 Nginx 拒绝；限流实现范围自相矛盾。

**建议**

- `auth_request` 只挂在受保护 API；为 `/api/v1/auth/login`、`/register`、`/public/`、`/actuator/health` 建显式公开 location，或让 verify 维护公开白名单并返回匿名 200。
- `/_auth` 增加内部 token；Nginx 对 `/internal/` 直接 `deny all`。
- `/ws/` 去掉 `auth_request`，由 Java 握手 `GETDEL` 校验 ticket；ticket 绑定 session + account。
- 内部认证先统一为共享 secret header，后续再 mTLS；不要同时保留两套未定方案。
- 限流：建议实现 Nginx `limit_req`（登录 / 注册 / AI），并修正 `03` 的“不做”描述。

### B2 会话恢复、关闭与录制就绪契约冲突

**现象**

- `05A:23/474-476`、`02:381`、`05C:819/898` 说断线即失败、不重连；但 `05C:507/934` 又写“重连快照”，`02:241` 把 REST `/start` `/end` 说成“页面刷新 / 异常恢复”的兜底。
- `session.snapshot` 没有 `last_seq`；客户端无法判断快照与事件流之间的缺口。
- `05A:474-476` / `02:476` 把任意 WS 关闭标记 failed，`05B:64` 把 track ended 标记 failed；正常结束停止 track 时可能把已完成 session 误判失败。
- `05A:137` 要求“三路录制就绪”才进入 `in_progress`，`05B:60` 说结构化面试只需 camera + audio；`02:236` 又统一要求“三路 uploaded 才能提交”。
- 没有 `recording.ready` 握手；`05C:1057-1059` 在 `session.start` 前启动录制和 multipart，服务端无法确认客户端真的就绪。
- 任务 session 定义了 `cancelled`，但没有任务 session cancel 端点；只有训练有 cancel。
- `05B:138/219` 临时录像保留“24 小时或任务关闭”，但 `05A:157` / `05C:391` 允许任务关闭后 24 小时内提交；关闭任务可能提前删掉唯一可提交录像。

**建议**

- 最终采用“控制 WS 断线 30 秒 grace + 重连快照”：保留“重连快照”，删除“页面刷新兜底”；页面刷新 / 录制器丢失 / Java 重启仍 failed，可重做。
- `session.snapshot` 增加 `last_seq`；连接时服务端从该 seq 之后补发事件，避免快照 / 事件竞态。
- 失败转移只允许从 `preparing / in_progress`；`ended / reviewing / submitted` 的正常关闭、track stop 不得改成 failed。
- 模式化 `required_streams`：自由 / 情景 camera + screen + audio；结构化面试 camera + audio；提交与 `RECORDING_INCOMPLETE` 按该集合校验。
- 增加 `recording.ready`（客户端三路 recorder 就绪）→ 服务端 ack → `session.start`；明确 multipart 由 Java 创建还是客户端调用。
- 增加任务 session cancel 端点 / WS 命令，清理 multipart 与临时录像。
- 临时录像保留期改为 `max(ended_at + 24h, task_closed_at + 24h)`；清理任务检查提交截止时间，不只检查任务状态。

### B3 时间基准、持久化与提交顺序未定义

**现象**

- 设计要求使用毫秒：`01` 的 `_ms` 字段、`05A:514-519`、`05B:154`、`06:271-274`。
- 需求仍有秒：`M3REQ:209/324`、`M4REQ:55/105/266`；`M3REQ:240` 又写毫秒。
- `01:81` 用 `sessions.duration_seconds`，`05A:374` / `05B:154` / `06:274` 用 `duration_ms`。
- `05A:516` 说 `at_ms` 0 是录制开始；`05B:62/117` 说 `offset_ms` 相对 session start；`05C:453` 从 `session.started` 起算；`05C:1057-1059` 在 `session.start` 前启动录制。三者可能不是同一个 t0。
- `05A:46/394` 说“事件先落库再推送”，`05A:487-503` 又说异步批量落库、JVM 重启会丢尾部；`05C:449` 重复“先落库再推送”。
- `05A:507-510` 要求提交前强制 flush，`05B:220` 要求三路 uploaded，`06:186-187` 在提交事务提交后触发评测；如果 submission 先提交、flush 后失败，M4 可能读到半份上下文。

**建议**

- 统一 t0：服务端接受 `session.start` 前完成 `recording.ready`；`session.started` 即 t0；所有 `at_ms`、`start_ms`、`end_ms`、`offset_ms`、`duration_ms` 都以该点为零。
- 最终：事件 / 文本 / 录制 / 报告时间点全链路毫秒；任务配置时长保留秒（教师按分钟输入），对外 DTO 用 `duration_ms`。
- 明确持久化边界：事件先进入有序持久化队列即可推送，DB 异步批量落库；关键事件（`session.ended`、`submission.created`、`interview.ended`、`session.failed`）同步 flush。不要声称“DB 提交后才推送”。
- 提交顺序固定为：停止采集 → flush 最后 part → 同步 flush 事件 / 文本 / 帧 → 校验 required streams → 插入 submission / 更新 session / 写 `submission.created` → commit → 触发 M4。flush 失败则不生成 submission。
- M4 的 60 秒对账不得为未 flush 的 submission 创建评测；以 submission 的 `created_at` 与 session 的 `ended_at` 做一致性检查。

### B4 M4 评测、partial 与回执契约冲突

**现象**

- `06:254` 说参考材料缺失只降低置信度，`06:262` 又把 `REFERENCE_MISSING` 放进 `partial_reasons`；`06:459-460` 把任何非空 `partial_reasons` 判为 partial，`06:267` 把任何缺失维度判为 partial；但 `06:252/663` 又说空事件、自由训练缺参考材料不 partial。
- 零权重维度缺失时，`06:128/144` 允许不参与总分，`06:161/459-460` 仍会把整体判为 partial，M7 随之 `ai_partial`。
- 回调幂等：`02:507` 用 `{job_id}`，`06:401/414/469` 用 `{job_id}:{attempt}`；`02:510` 按 `evaluation_id` 幂等；`06:455` 新 attempt 覆盖，`06:526` 旧 attempt 返回 200 ignored，`06:527` 更高 attempt 409。
- `01:110` 的 `evaluation_jobs.status` 没有在成功路径明确更新；调度器扫描 stale running 时可能重投已完成评测。
- `01:109` 的 `input_snapshots` 缺 `source_type` / `source_id` / `submission_id` / `training_record_id` / `task_config_version` / `training_config_version`；`06:349` 又会更新 `flags`，与“快照不可变”冲突。
- `06:117` 说维度置信度由子项置信度加权，但回调 / prompt 只有子项分和一个维度级 confidence，`01:107` 无子项置信度。
- `06:636/869` 的 3—5 条建议与 `/issues` 全部问题没有区分字段；`01:108` 只有 `sort_order`。
- `06:579-580` 同时统计 `classroom.question_asked(intent=student_question)` 与 `student.question`，学生会重复计数。
- `07:331` 依赖 `EvaluationTerminalEvent`，但 06/02 没有事件定义；`06:166` 又说 M7 只消费 completed，无法产生 `ai_partial/ai_failed`。

**建议**

- 把 `warnings` 与 `partial_reasons` 分开：参考材料缺失、空事件、低置信 OCR 只降置信度 / 记 warning；`partial_reasons` 只用于缺失适用维度或必需输入。
- 明确零权重维度：缺失时不参与总分、不判 partial；若判 partial，则 M7 的零权重逻辑失效。建议“权重 0 维度缺失 → completed + warning”。
- 回调统一以 `(evaluation_id, attempt)` 为幂等键；在 result 事务内原子更新 `evaluations`、`dimension_scores`、`issues`、`evaluation_jobs`；终态后拒绝任何 attempt；明确同 / 旧 / 高 attempt 的 HTTP 与 XACK 行为。
- 调度器 stale 扫描与 XAUTOCLAIM 使用同一 lease / attempt 规则，避免同一 attempt 并发执行。
- 补齐 `input_snapshots` 字段；把运行期 `flags / context_truncated` 放进单独的 `evaluation_input_status` 或明确允许更新；`recording_ids` 定义为 stream 记录 ID 数组。
- 子项置信度：要么在 LLM schema / callback / 表里增加 `sub_confidences`，要么删除“加权平均”说法，直接使用维度 confidence。
- 建议增加 `issues.is_suggestion` / `suggestion_rank`，或独立 `evaluation_suggestions` 表。
- 互动统计只保留一个学生提问计数来源。
- 定义 `EvaluationTerminalEvent`（evaluation_id、source_type、source_id、status、completed_at、attempt），after-commit 发布；M7 同时消费 completed / partial / failed 以生成最终状态。

### B5 训练隐私可被通用接口绕过

**现象**

- `08:433/641-643`、`05B:165/205`、`06:930/940` 规定训练录像 / 报告仅学生本人可见。
- 但 `02:138-142` 给教师 `session:read`、`session:replay`、`session:events:read`、`evaluation:read`（本课程）；`02:219-226/248-250` 的通用 session / replay / texts / recordings / report / issues 接口没有 `session_type=training` 或 `source_type=training_record` 排除规则。
- 教师拿到 training session / evaluation ID 即可读取训练转写、回放和报告；M6 专用接口的 403 不足以保护。

**建议**

- 在 service 层统一加硬规则：`session_type='training'` 的 session / recording / text / frame / event / replay，以及 `source_type='training_record'` 的 evaluation / report / issues，仅 `student_account_id` 本人可访问。
- 教师权限只适用于 `session_type='task'` / `source_type='task_submission'`。
- 安全测试必须覆盖通用接口，不只 `/training/records/{id}/evaluation`。

### B6 数据模型枚举、清理根、外键与面试映射缺失

**现象**

- `01:13` 要求 `varchar + check`，但 `submissions.status`、`sessions.session_type`、`sessions.mode`、`frames.status`、`session_texts.status`、`school_admins.status`、专业 / 班级 / 类别 / 题目状态的取值未列全。
- `sessions.status` 混合任务与训练状态；没有约束“训练不能 submitted / 任务不能 selected/evaluated”。
- `01` 说 M3 数据“按 session 删除”，但 `submissions.session_id` 没有 `ON DELETE`；删除已提交 session 会受 FK 阻塞，或必须先删 submission 并级联 M4/M7。清理根不明确。
- `frames` 没有 status，但 `05A:104` 写 pending；`session_texts.status` 也没有定义。
- `evaluations` 多态来源没有 CHECK 保证 `submission_id` / `training_record_id` 恰好一个；`training_records.evaluation_id` 与 `evaluations.training_record_id` 重复且无 FK。
- `final_scores.ai_evaluation_id` / `teacher_score_id` 无 FK / ON DELETE；清空教师评分可能留下悬挂引用。
- 面试 `answer_id` / `question_id` 无持久化表；`01:97` 只把它们塞进 `session_texts.speaker_ref`，没有定义题目 / 回答映射。
- `01:29` 的 M6 表清单漏 `training_materials`；`01:95` 的录像对象键没有训练分支，训练 `task_id=null`。

**建议**

- 发布“枚举与约束附录”：所有状态字段的取值、CHECK、状态转移；`session_type IN ('task','training')`、`mode IN ('free','scenario','interview')`、`(session_type='training') = (task_id IS NULL)`。
- 明确两个清理根：任务提交件（先删 MinIO，再删 submission → 级联 M4/M7，最后删 session → 级联录像 / 文本 / 帧 / 事件）和训练记录（删 record → 级联 evaluation / session / 录像）。临时未提交 attempt 单独按 24h / 5 个清理。
- 为 `final_scores` 增加 `teacher_score_id → teacher_scores.id ON DELETE SET NULL`、`ai_evaluation_id → evaluations.id ON DELETE SET NULL`；为 `training_templates`、`training_records`、`training_materials`、`task_grading_configs`、`teacher_scores.graded_by` 补 FK 或明确不建 FK。
- 面试映射二选一：新增 `m3.interview_questions` / `interview_answers`，或明确 `answer_id` 是事件派生键，并写出 M4 的 join 规则。
- 补 `frames.status`（pending/processed/failed）、`session_texts.status`（partial/final）、`submissions.status`（建议只保留 submitted）；补 `training_materials` 到 schema 清单；统一录像对象键。
