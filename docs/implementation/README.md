## 阅读顺序

1. 先读 `15-代码规范与骨架` 的包结构 / 命名 / 事务 / 事件约定。
2. 再读 `14-后端代码实现设计` 的整体类清单与跨模块事件。
3. 生成某模块代码前，读对应模块本文档。
4. 需要接口字段时回查 [02 API](../design/02-API与实时协议.md)；需要表 / 字段时回查 [12 数据库设计](../design/12-数据库设计.md)。

## 代码生成约定

- 文档中的方法签名是契约；实现可以拆私有方法，但不要改输入 / 输出 / 事务语义。
- 不跨模块 import `domain` / `infrastructure`；只调用 application 接口或订阅集成事件。
- Controller 不写业务；ApplicationService 管事务；Domain 管规则；Port / Repository 管外部。
- 事件 after-commit；监听器幂等；reconciler 兜底。
- 每个模块至少：domain 单测、application 集成测试、权限用例、契约 fixture、对应 E2E 场景；见 [10 测试与验收](../design/10-测试与验收.md) 第 2 节。
- 代码目录建议：`server/`（Java）、`ai/`（Python）；设计确认后再创建。

## 修改边界

- 只修改自己负责模块的实现设计；跨模块修改先按 [01](../team/01-模块归属与修改规则.md) 第 4.2 / 5 节确认。
- 文档中的方法签名是契约；改签名、事务语义、事件或表字段，先改 `02` / `12` / `14` 并通知下游 owner。
- 不在他人模块的文档里做“顺手修正”；发现问题提交给对应 owner。
- 更新本表或模块状态时，只改自己行；汇总由 Score/QA Owner 核对。

## 测试要求

- 单元 → 集成 → 契约 → E2E 四层都要有；性能 / 安全 / 迁移按模块风险补。
- 测试文件路径属于模块边界：`server/src/test/java/.../mX/**`、`ai/tests/**`、`frontend/**/*.spec.ts`；`e2e/**` 由 Score/QA Owner 维护。
- 模块完成度与测试执行状态同步到 [进度看板](../team/02-进度看板.md)；没有测试报告不填完成。
